# Database Architecture

Maara uses a split database ownership model: a Zerocraft-owned Platform DB and
customer-owned Supabase projects. This document summarizes the architecture;
detailed schema definitions are in the referenced documents.

## Platform DB (`maara`)

Owned by Zerocraft. Holds central users, organizations, memberships,
invitations, stores, OAuth connections, tenant mappings, jobs, and audit events.
No commerce data ever lives in the Platform DB.

- **Migration:** `infrastructure/supabase/migrations/`
- **Local config:** `infrastructure/supabase/config.toml`
- **Tests:** `infrastructure/supabase/tests/`
- **Design:** `docs/architecture/database-ownership.md`

## Customer-owned Supabase projects

Each tenant store gets its own independent Supabase project holding commerce
data (catalog, inventory, orders, customers, payments, shipping, POS, media).
No Platform data ever lives in a customer project.

- **Template:** `templates/commerce/` (versioned, customer-owned schema)
- **Schema:** `docs/database/schema.md`
- **Relationships:** `docs/database/relationships.md`
- **Template schema:** `templates/commerce/docs/schema.md`
- **Template ownership:** `templates/commerce/docs/ownership.md`
- **Template migration policy:** `templates/commerce/docs/migration-policy.md`

## Core data principles

| Principle | Rule |
| --- | --- |
| Keys | UUID primary keys, `default gen_random_uuid()` |
| Tenancy | `organization_id` on every business table |
| Money | `bigint` integer paise; percentages in basis points |
| Time | `timestamptz` for `created_at`/`updated_at` |
| Audit columns | `created_by`, `updated_by`, `created_at`, `updated_at` |
| Soft delete | Status / `archived_at` columns; hard delete only where history permits |

## RLS and authorization

- RLS enabled on every exposed table; policies combine tenant membership and
  permission checks.
- `TO authenticated` is necessary but never sufficient.
- Every `UPDATE` policy has both `USING` and `WITH CHECK`.
- `WITH CHECK` repeats the tenant predicate, preventing a row from being moved
  to another organization.
- No policy uses `user_metadata` or an unverified header.

See `docs/security/rls-policies.md` for the complete policy matrix and helper
functions.
