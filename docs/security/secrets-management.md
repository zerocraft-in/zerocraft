# Secrets Management

## Principle

No plaintext secrets are stored in the Platform DB, in code, or in logs. All
sensitive values are either encrypted at rest or stored as references to an
external secret vault.

## What Is Stored Where

| Secret | Storage Location | Format |
|---|---|---|
| Supabase OAuth access token | `supabase_oauth_tokens.access_token_ciphertext` | AES-256-GCM ciphertext |
| Supabase OAuth refresh token | `supabase_oauth_tokens.refresh_token_ciphertext` | AES-256-GCM ciphertext |
| OAuth PKCE verifier | `supabase_oauth_states.code_verifier_ciphertext` | AES-256-GCM ciphertext |
| Tenant database password | Cloudflare KV `TENANT_SECRETS` | Plaintext in KV, referenced by `tenant_databases.database_password_secret_ref` |
| Platform service-role key | Cloudflare secret (`SUPABASE_PLATFORM_SERVICE_ROLE_KEY`) | Worker secret, never in code |
| OAuth encryption key | Cloudflare secret (`OAUTH_TOKEN_ENCRYPTION_KEY`) | Worker secret, never in code |
| Provisioner shared secret | Cloudflare secret (`PROVISIONER_SHARED_SECRET`) | Worker secret, never in code |

## Encryption

- **Algorithm**: AES-256-GCM with a 12-byte random nonce per encryption
- **Key**: 32 bytes, provided as base64-encoded Cloudflare secret
- **Key rotation**: `key_id` stored alongside ciphertext. The `OAUTH_ENCRYPTION_KEY_ID`
  env var identifies the active key version. Decryption tries the key referenced
  by the stored `key_id`.
- **Additional data**: Fixed AAD `"zerocraft.supabase.oauth.v1"` binds ciphertext
  to the application context.
- **Nonce**: Random 96-bit IV per operation, stored alongside ciphertext.

## Token Lifecycle

1. **Exchange**: Authorization code → access + refresh tokens via Management API
2. **Encrypt**: Both tokens encrypted with AES-256-GCM before storage
3. **Store**: Ciphertext written to `supabase_oauth_tokens` (service role only)
4. **Use**: Decrypted in memory only, placed in `Authorization` header, never logged
5. **Refresh**: On 401/403 or expiry within 10 minutes, refresh token used to
   obtain new access token; both re-encrypted and stored
6. **Revoke**: On refresh failure, connection marked `needs_reauth`, job marked
   `NEEDS_REAUTHORIZATION`

## Tenant Database Passwords

- Generated by the Worker (40 chars, all character classes)
- Required by Supabase Management API `POST /v1/projects` (`db_pass`)
- **Never** stored in Platform DB
- Written to Cloudflare KV `TENANT_SECRETS` at `tenant/{project_ref}/db_password`
- Referenced from `tenant_databases.database_password_secret_ref` as
  `kv://tenant-secrets/tenant/{project_ref}/db_password`
- The password is not needed after project creation (Management API handles
  auth via the OAuth access token)

## What Is NOT Stored

- Plaintext OAuth tokens anywhere
- Plaintext database passwords in Platform DB
- Service-role keys in client-side code or environment variables with `NEXT_PUBLIC_`
- JWTs or tokens in error messages (redacted via `sanitizeError()`)
- Supabase project db_pass in `wrangler.toml` or `vars`

## Rotation

To rotate the OAuth encryption key:

1. Generate a new 32-byte base64 key.
2. Set it as `OAUTH_TOKEN_ENCRYPTION_KEY` with a new `OAUTH_ENCRYPTION_KEY_ID`.
3. Existing ciphertext remains decryptable via the stored `key_id` — the Worker
   imports the key referenced by each row's `key_id`.
4. On next token refresh, the new key is used for re-encryption.
